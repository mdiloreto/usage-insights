## Goals / Non-Goals

**Goals:** Match the native compact bar and detail experience; preserve the approved canary's Follow Space default and never substitute an unavailable remote; expose per-machine token history and independent quota status; show observed plan, Frontier credit and monthly spend with Anthropic-compatible semantics while failing closed; keep the Mac's existing local store and visualize Linux through its existing host-local cache.

**Non-goals:** Cross-host quota maxima or sums; aggregate-only fleet charts that erase per-host history; routine coverage dashboards; new auth flows, credentials, account switching, model turns, or provider APIs for every CLI; GitHub writes or publishing; GitHub Copilot quota; Console API credits; replacement of the upstream GaganSD work; Windows support promises; normal layout changes; deployment outside the existing isolated Mac canary.

## Decisions

### 1. Add a native-style compact bar with click-through details

The bar is a companion inside the existing native `usage-limits` surface, not a new layout. It has two modes:

- **Follow Space (default, matching the canary):** show only the current space's machine. A local space shows this computer; a remote space shows that remote. Do not add Local + Remote automatically.
- **Local + Remote:** show this computer plus one explicitly selected remote. When more than one remote is available, offer a chooser. Keep the selected remote named when it is unavailable or non-enrolled; never substitute another remote, a local reading, or a fleet value.

With zero registered remotes, leave the original Local-only bar and native tooltips exactly unchanged: no new Local label, mode control, empty Remote group or detail control. Registered but unconfigured remotes can still be listed in the detail surface with a reason.

Clicking the detail control always opens full details for every connected remote and this computer. The surface shows native provider icons, original meters and tooltips, provider/window labels, source, age, reset/pace when available, the optional-window setting including Fable only when a verified Fable reading exists, and a refresh control named for the machine and provider. A selected unavailable or registered non-enrolled machine remains visible with its safe reason. Details do not move or relabel account readings.

In Local + Remote, keep both groups identifiable as the bar narrows. Reuse native styling: full meters first, then labeled percentages without meters, then one identified window per provider per machine (highest used among eligible windows, sooner reset breaks ties). At the physical minimum keep both named detail controls, never an unlabeled percentage. A provider without a current reading shows its icon and `—`; details explain why and contain any eligible dated history. Follow Space has only its one group and uses the same compaction order. No-remote styling, settings and local refresh semantics stay unchanged. Focused-session counters remain separate: when focus moves to Linux, do not pass a remote PID or terminal ID to a local helper or show an old local session as current. Remote focused-session context is unavailable in this increment; a future change requires proven owning-host binding. Focus does not relabel account readings, and existing local settings do not change remote enrollment, account selection, or refresh permission.

### 2. One explicit, host-installed quota helper over Herdr exec

After operator installation and separate opt-in per registered remote, use the existing `herdr.exec` connection with a fixed executable and argument shape: allowlisted operation/provider IDs and one validated binding digest. The native target goes only through `on`; no user-provided shell, command, path, executable, account selector, or elevated identity. Use a constant launcher/check at the approved helper entrypoint to return a reserved safe result for an actually verified missing helper (or a proven typed equivalent). Do not infer that state from a rejected exec, parse raw stderr, or emit raw rejection text. A trusted connection signal can establish offline/denied; ambiguous transport failures remain unknown. An installed helper distinguishing missing CLI from auth or unsupported plan is a separate layer.

- **Independent quota enrollment:** Record the exact registered route, a fresh local grant generation, an enrollment-scoped fingerprint of the verified Core ID, and the independently confirmed host opt-in/install binding. Use a fresh trusted `machine.list` result to verify the route and fingerprint. App 0.1.16/Core 0.1.20 accepts the transient verified Core ID in `on`, but Core also resolves legal names there: reject observed ambiguity and never treat `on` or before/after listing alone as an atomic identity check. Do not persist or log raw Core IDs or raw machine-list records in quota state.
- **Receiver-side binding:** The one binding argument is a nonsecret, exactly 64-lowercase-hex SHA-256 digest of a versioned domain, the verified Core ID and the host-owned opt-in marker. Under the host lock, the helper validates the shape and recomputes it from the marker and its **own** Core identity obtained through a pinned, bounded, existing-Core-only metadata path. Missing, invalid or mismatched binding denies cache reads and provider probes. A successful response carries the verified digest for the viewer to check before publishing, not the raw marker or ID. The digest is not a credential or account selector and is not exposed in the projection. The fixture used `hc server status --json` against the receiving Core's inherited Linux socket; qualify the production metadata path before use.
- **Continuity and revocation:** Quota opt-in is independently revocable. An unobserved out-of-band remove/re-add with the same Core, exact route and unchanged marker continues the existing grant because this runtime exposes no registration incarnation. An observed removal or a verified different Core/route disables the old grant and requires explicit re-enrollment; a transient offline state alone is not revocation. Managed revocation invalidates the local grant/projection before host-side changes; a managed new install or grant rotates the host marker and uses a fresh local generation. Host-only rotation blocks subsequent old-digest requests but is not instant viewer revocation of an already completed reply. Before attaching a result, verify the current binding and commit only against the still-current grant and operation generations.
- `read`: address one enrolled machine/provider pair, return its eligible cached evidence and attempt that provider only if enabled and due. No polling simply because a host is discovered.
- `refresh`: request one fresh check for one named machine/provider; if blocked or already in flight, report that or join the same flight. Report whether fresh evidence was obtained, delayed, or failed, with retry timing when available. It is not a rescan of every provider or host.
- Codex and Claude adapters use the CLI and existing sign-in on that host, with one current host-scoped CLI identity per provider. The CLI may perform its normal host-local authentication behavior; the feature must not trigger a sign-in, move OAuth/keychain material to the Mac, change account, or send a model prompt. The first phase reuses the native normalization and display semantics; it does not rewrite existing local collectors or require their current raw formats as a permanent protocol. Additional identities/providers are future qualified adapters, not automatic discovery.
- **Anthropic-compatible readings:** Keep plan entitlement, credit and spend as separate typed records. Plan windows are 5h, weekly and model-scoped windows such as Fable only when the provider returns them. Frontier credit is a distinct credit, not a plan window. Monthly usage credits/spend carries amount, currency/unit, cap and reset only when the verified reading contains them; a date-only reset stays a dated label rather than a fabricated instant. Missing or ambiguous fields are unavailable, never zero, estimated or defaulted. The primary Claude `get_usage` path has returned no usable windows in live testing; the Frontier-only fallback is bounded to at most Frontier credit and monthly spend. Do not infer 5h/weekly/Fable entitlement from sign-in, plan name, Frontier or spend.
- **Same-account comparison:** Present plan and Frontier as comparable only when both readings bind to the same verified provider account generation. Sign-in success is not account proof. Otherwise show each separately as uncomparable or unavailable and compute no difference, ratio or total.
- **Monetary fail-closed:** Use only fields already exposed by the qualified CLI reading. If the source is absent, unreadable, ambiguous or unstable, show unavailable. Do not add an API, scrape Console, or prescribe a new data source for amounts, units or reset. Console API credits are a separate follow-up; see the follow-up note below.
- Impose per-provider deadlines, process cleanup, bounded output and schema validation at both ends. Return only sanitized normalized records: protocol version and capabilities as available; provider, optional safe plan, reading type (plan window, credit or spend), source kind, windows (ID/name, used percent, amount/unit/cap when observed, duration/reset if known), provider observation time, attempt time, and read time; separate provider and transport outcomes. Use safe typed reasons for missing helper, missing CLI, expired auth, unsupported/no subscription, malformed payload, estimated evidence, paused, rate-limited, no usable plan windows, Frontier-only, unavailable monetary data, and unavailable/unknown transport. Keep stdout standardized; no raw provider output, credential values, transcripts, sensitive paths or diagnostic stderr cross the boundary. Unknown fields/versions must not be assumed valid measurements.
- Use host-owned private atomic state under per-provider locks to keep cooldown, backoff and eligible last-good evidence across helper invocations. The host lock and due check are authoritative across viewer processes, handoffs, and restarts. The viewer neither reads nor writes the file. The planned starting cadence mirrors native: 5 minutes between regular checks, stale after 15 minutes, hourly retry for missing CLI, and 30 seconds of manual refresh cooldown, with additional per-provider backoff. Qualify and tighten those timings as needed. Staleness comes from observation, not file mtime, read time or a failed attempt. A passed reset does not produce zero: show waiting for a fresh window and retain eligible history with its original timestamp and age. Genuine 0% and 100% are valid measurements. Mark estimates and dated fallbacks as such.
- Key observations and in-flight results to enrolled machine identity/generation and the verified host-scoped provider identity/generation; never match identities by machine, plan, or account display names. On failed reads, last confirmed evidence may only be shown as history for that verified generation; if the identity boundary cannot be established, suppress numeric fallback. Invalidate on replacement, re-enrollment, or provider account change and discard late results. Keep same-provider readings on different machines separate even when the accounts might be the same.

**Alternatives.** A passive external-file-only reader was mechanically demonstrated, but assumes another exporter and cannot provide native manual refresh parity. A passive snapshot plus an opt-in host timer would decouple provider calls and keep evidence fresher with the viewer closed; it adds another scheduler with lifecycle cost, and viewer refresh would still only reread a snapshot. Inlining raw shell probes over exec would couple untrusted parsing and host environment details to the viewer. Calling provider APIs from the Mac would cross the host auth boundary. The demand-driven one-shot choice costs one explicit installation and enrollment per host; closed viewers start no new probes, and no independent host quota timer is added without a separate decision. Console API credits, GitHub Copilot quota and a GitHub-published fleet cache are excluded: each needs a different account or publication boundary and would not preserve the local-only, fail-closed constraints. Borrow [Omarchy's](https://github.com/basecamp/omarchy/blob/v4.5.0/shell/plugins/agents/README.md) normalized records, dated last-good, cadence ideas, and selected-window UI; do not borrow shared folders, maximum aggregation, reset-to-zero, account switching, or the separate [released mod's tightest-available summary](https://github.com/mdiloreto/herdr-fleet-quota/blob/v0.2.3/README.md#what-it-shows).

### 3. One viewer-side quota coordinator and shared projection

One viewer-owned coordinator is responsible for remote quota work inside one native App process/runtime. On a healthy supported runtime with an enrolled helper enabled, Insights alone must actually receive updates without the bar. Bar and Insights read a versioned shared projection; refresh controls send a targeted intent to the coordinator rather than invoking a provider independently. Compatible mounted copies use a short synchronous shared read/set to claim or renew a bounded owner lease, without visibility commands or subprocesses. A hidden but mounted owner may keep the lease and continue due work for opted-in hosts, including when it is the only mounted consumer. Removal releases its lease; an expired lease allows a successor. With no compatible mounted consumer there is no new work. Keep one in-flight operation per machine generation/provider and distinguish waiting, owner unavailable, and cached/stale. An incompatible copy must not write the coordinator state or start a second poller. Do not import files across installed mods. Keep existing native Local quota refresh behavior, and share its normalized projection without starting another local collector.

Check `checking()` before starting timers, ownership mutations or I/O. Each live runtime uses a fresh in-memory incarnation ID (`crypto.randomUUID()` in the shared JS runtime) and monotonic lease timing (`performance.now()` in the fixture); persisted ownership or projection is not proof of liveness. Dispose releases only the matching owner lease, not the separate flight guard: the child may outlive the view or the App. At handoff or startup, fence surviving work until settlement or a qualified bound, discard stale results by runtime, ownership, and enrollment/provider generation, and rely on the host lock rather than viewer-side timers for cross-process exclusion. The projection is local to the viewer: no GitHub write, upload or external publish is part of this design.

Before implementing this integration, prove scope, lifetime, coordination and handoff of native shared state across mod copies and windows in a stub home. If the runtime cannot support a single producer with a visible dashboard alone, stop and review the ownership design; do not make the bar implicit infrastructure or silently add a second reader that probes.

### 4. Add machine scopes and per-host history without redesigning Insights

Keep the current dashboard components, visual hierarchy, filters, chart, heatmap and host-local indexers. The selector uses English **All**, **This Computer** and named remotes. This Computer reads the Mac's existing local Insights store; each remote scope reads only that machine's existing host-local cache through the fleet path. Do not add a Mac collector, publisher, GitHub write, raw transcript transfer, or cross-host quota arithmetic.

All combines measured rows from this computer and readable remotes for the existing totals and heatmap, and the chart visibly distinguishes each machine's contribution alongside the aggregate. Keep origin on rows and namespace per-host session identity so equal IDs cannot erase a host's contribution. A per-host contribution is not satisfied by a counter or a single combined series. Count readable stale caches only with their freshness available; exclude unreadable caches instead of treating them as zero. A single-machine scope uses only that machine's rows for history, totals, trends, drill-downs and quotas. Never relabel old async results after a scope or filter change.

Do not show a routine technical coverage card. When a machine is stale or unreadable, show one compact inline note naming that machine, its freshness and safe reason, only when needed. Quota sections remain independent of token filters, read errors and cadence; stack them by machine, local first, in All and filter them in a single scope. Keep export explicitly local in v1; disable it with a reason in All and remote scopes.

## Risks / Trade-offs

- **False parity and auth side effects:** Mac fixture success and transport success do not prove Linux parity. Qualify real Codex multi-bucket and Claude modern/legacy paths with fixtures and a signed-in portable Linux canary; prove that checks cannot probe production and that no prompts, sign-ins, or raw account data escape. Claude plan windows remain unqualified after the no-usable-window live result; do not present Frontier credit or monthly spend as plan parity.
- **Manufactured monetary confidence:** A displayed dollar amount, cap or reset is not the same as a resolved entitlement. Show only observed fields, keep ambiguous or absent fields unavailable, and never estimate, default to zero, or invent units or reset instants. Console API credits stay out of scope.
- **Host identity and stale evidence:** Connection/layout names can outlast or change with the registration, and account switches may lack a safe identifier. Fail closed rather than reattach old numbers; test replacement, reconnect, spoofed labels and clock/reset boundaries. Do not compare plan and Frontier unless both bind to the same verified account generation.
- **Slow or duplicate work:** Validate helper timeouts, single-flight, per-provider backoff, and ownership across bar/dashboard or multiple windows so one remote cannot block Local or unrelated hosts.
- **Hidden degradation after removing the coverage card:** A routine coverage card is removed to reduce noise, so the inline notice must reliably name the affected machine and freshness. Test healthy, stale, unreadable and selected-unavailable states; do not replace the card with a silent zero.
- **Density and focus:** The compact bar must stay usable on a narrow window and at real zoom. Verify these interactions in a disposable app home before staging, and review them with a human before promoting the canary.
- **Upstream divergence:** The GaganSD #130/#158 machine-scope work overlaps the Insights direction. Treat it as later coordination and comparison evidence; do not replace this prototype, its fixtures or its quota/identity constraints with an unqualified upstream implementation.
